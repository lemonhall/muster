- residual_risks:
  1. 同模型自评的橡皮图章风险（与 M0–M7 相同）。缓解：结论一律落成可复现命令或永久门禁。
  2. **没有线上验收**（同 M3–M7）：整套 M8 只在本地 workerd / 本地 `wrangler dev --local`
     上验证。`npm run e2e` 现在是"真进程 + 真 HTTP/WS"，于是**跨请求的 I/O 边界**这一层
     已经被真实覆盖（偏差 15 就是这么抓出来的）；但真实边缘上的装载延迟、冷启动、
     isolate 复用寿命，以及租户模块数量上去之后的 D1 装载路径耗时，仍然没有实测。
  3. **运行时只支持 JS**（[ECN-0012](../ecn/ECN-0012-runtime-modules-on-worker-loader.md)
     偏差 4）：上游的 Lua 模块（`internal/gopher-lua`）不在本移植范围内。用 Lua 写的
     现成模块无法直接搬过来，必须改写为 ESM。
  4. **未实现的 `nk.*` 是"不存在"而不是"报明确的不支持"**（ECN-0012 偏差 11）：
     模块调用 `nk.sqlExec` 之类的未实现能力会撞上 `TypeError`，而不是一条"该能力未实现"
     的自定义错误。这是刻意的诚实失败，但错误信息对模块作者不够友好。
  5. **能力对象的生命周期只有一次调用**（ECN-0012 偏差 14）：`nk` / `logger` 必须从
     handler / hook 的入参里取；在 `InitModule` 里捕获一份留到以后用，第二次调用会
     `RPC stub used after being disposed`。偏差 14 直接来自 DoD 8 的实测。
  6. **对局 tick 循环与 `registerMatch` 仍未落地**（M7 偏差 11 的后半段）：M8 的运行时
     是"请求驱动的模块宿主"，而 tick 需要"对局 DO 里的高频率定时器"这一套载体，
     两者机制不同，覆盖矩阵按此把它排在 M9 之后的运行时增量。
  7. **测试收尾噪声**：同时开真 WebSocket、且新建租户的用例文件（`tests/integration/party/`、
     `tests/integration/match/`、`tests/integration/channel/`）在 vitest 收尾时会打一条
     `uncaught exception ... EnvironmentTeardownError`。**不影响退出码**（全绿），
     与 M7 记录的同一现象同源；M8 只做"记录在案"，没有动它。

| MAJOR | contract::runtime::handler-calling-convention | 宿主调用模块 handler 时传的是 `(ctx, payload)`。于是模块只能去捕获 `InitModule` 那一份 `nk`；而那份背后的 RPC 会话在第一次调用结束时就关闭，第二次调用必然拿到 `RPC stub used after being disposed`。`tests/integration/runtime/tools.test.ts` 首次运行当场变红：`test_storage_read_returns_empty_values_for_empty_objects` 与 `test_notifications_delete_removes_the_row` 同报 `RPC stub used after being disposed` | 已修复：`src/runtime/bridge.ts` 新增 `callArgs(host, ctx, payloads)`，入参逐位对齐上游 `RuntimeJS.InvokeFunction` 的 `[ctx, logger, nk, ...payloads]`；模块必须从 handler / hook 的参数里取 `nk` 与 `logger`。登记为 ECN-0012 偏差 14，并回改 `modules.test.ts` / `tools.test.ts` / `rpc.test.ts` / `hooks.test.ts` 的模块样例 |

# ECN-0002: 邮箱认证的密码哈希改用 PBKDF2-SHA256

## 基本信息

- **ECN 编号**：ECN-0002
- **关联 PRD**：PRD-0001
- **关联 Req ID**：REQ-0001-003（认证方式与服务端密钥）
- **发现阶段**：v1-identity-storage（M1）编码中
- **日期**：2026-09-28

## 变更原因

上游参考实现对邮箱账号的密码用 **bcrypt** 存库。本项目跑在 workerd 上，而 workerd 的
`crypto.subtle` 只提供 WebCrypto 定义的算法族——**没有 bcrypt，也没有 scrypt**。

可选的三条路：

1. 引入纯 JS 的 bcrypt 实现：bcrypt 的代价因子是为"慢"而设计的，纯 JS 实现（无 SIMD、
   无原生加速）在 Worker 的 CPU 预算里会吃掉大几十毫秒，且这部分时间是**攻击者可控的**
   （每个登录请求都要付一次）——等于把 Worker 的 CPU 限制变成可利用的拒绝服务面。
2. 把哈希放到 Durable Object / Queue 里异步算：把一次同步登录拆成"提交 + 轮询"，
   直接改变了对客户端可观测的交互形状（上游是同步返回会话）。
3. 换一个 WebCrypto 原生、且同属"口令派生函数"家族的算法：**PBKDF2**。

选 3。这是本项目在**内部存储形态**上的偏差，不是协议偏差。

## 变更内容

### 原设计

- 密码列存 bcrypt 的 `$2a$...` 字符串（与上游同款）。

### 新设计

- 密码列存：`pbkdf2-sha256$<iterations>$<salt-b64url>$<hash-b64url>`
  - `<iterations>` = 100000（默认值，落进记录里，将来可提高而不锁死旧账号）；
  - `<salt>` = 16 字节随机盐（每用户独立，`crypto.getRandomValues`）；
  - `<hash>` = PBKDF2-HMAC-SHA256，256 bit 输出；
  - 校验用**恒时比较**（逐字节异或累积），不用 `===`。
- 自描述格式：算法名与轮数都写在记录里。将来换成更强的参数或算法时，旧记录仍可识别与校验，
  不需要"全员改密"。

### 为什么这个偏差是可接受的

可观测面**没有变化**，逐条说明：

| 对外可观测项 | 是否变化 | 说明 |
|---|---|---|
| 请求形状 | 否 | 客户端发的是明文密码，与上游一致 |
| 响应形状 | 否 | 登录成功/失败的 body、状态码、消息逐字对齐上游 |
| 错误消息 | 否 | `Invalid credentials.` / `Password must be at least 8 characters long.` 等照抄 |
| 密码策略 | 否 | 长度阈值由 API 层判，与哈希算法无关 |
| 库内数据 | 是 | 哈希字符串形态不同——**这是内部状态，不是协议** |

### 明确不做

- 不做 bcrypt 兼容层（能读上游 bcrypt 记录）：本项目不导入上游的库，没有需要兼容的历史数据；
  真要做迁移也应作为一次性导入工具再登记独立 ECN。
- 不做"按租户配置哈希算法"：v1 的哈希参数是全局常量，租户维度只影响盐与库分区。
